## Purpose 
The skill provides a structured, multidimensional code-review process intended to improve software quality before changes are merged. It evaluates code across five dimensions:
- **Correctness**: Compliance with specifications, edge cases, error handling, and test effectiveness.
- **Readability and simplicity**: Naming, control flow, maintainability, unnecessary complexity, and dead code.
- **Architecture**: Module boundaries, dependencies, duplication, abstractions, and consistency with existing design.
- **Security**: Input validation, authentication, authorization, secret handling, and untrusted external data.
- **Performance**: Query efficiency, bounded operations, pagination, unnecessary rendering, and resource usage.

The skill also recommends focused changes, actionable review findings, dependency scrutiny, verification of test evidence, and human involvement in final decisions.

## Trigger / Description 
The skill should activate when:
- A pull request or code change needs review before merging.
- A feature implementation has been completed.
- Code generated by another agent or developer needs evaluation.
- When refactoring existing code.
- A bug fix needs verification.

Its workflow is broadly organized as follows:
1. Understand the purpose and requirements of the change.
2. Inspect tests first to evaluate intent and coverage.
3. Review the implementation across the five quality dimensions.
4. Categorize findings by severity and importance.
5. Verify the author's testing and build evidence.

## Tools / Commands / Permissions 
The skill does not define one mandatory toolset. It expects the coding agent to use the capabilities available in its environment.

Tools and activities mentioned or implied:
- Read source code, diffs, specifications, tests, and project conventions.
- Execute relevant tests and builds.
- Inspect test quality and, where appropriate, perform mutation testing.
- Review dependency manifests, lockfiles, changelogs, and dependency advisories.
- Use security and performance analysis tools when relevant.
- Inspect manual-verification evidence, screenshots, and before/after measurements.
- Identify dead code and ask before deleting uncertain unused elements.
- Performance tools such as Lighthouse, DevTools and bundle analyzers in the performance checklist.

Commands mentioned in the skill or its references include:
- `npm audit` for dependency advisory checks.
- `git diff --cached | grep -i "password\|secret\|api_key\|token"` as an example secret check.
- Package-manager-specific frozen or immutable installation and audit commands in the security checklist.

Permissions assessment:
The skill does not enforce a read-only operating mode. Some instructions, especially mutation testing, require modifying code temporarily and restoring it. Test execution, package installation, and other diagnostic commands can also have side effects depending on the project.

## Potential Risks 
1. Mutation testing can modify repository files. The skill explicitly suggests inverting a condition, running the tests, and restoring the file. This conflicts with a workflow that prohibits repository modifications unless the activity is isolated and separately authorized.
2. Review actions are not explicitly restricted to read-only operations. The skill discusses approval standards and review comments, including severity labels. Without additional instructions, an agent might confuse generating a recommendation with submitting an actual GitHub review.
3. Testing commands can have side effects. Dependency installation, lifecycle scripts, external service calls, and test fixtures may change files or shared resources. Commands should be inspected and executed only in a suitable environment.
4. Some recommendations are opinionated. Suggested change-size thresholds, file-size signals, and architectural preferences are useful heuristics, not universal rules. They should be evaluated against project conventions and requirements.
5. The review scope is broader than PR readiness. The skill includes refactoring advice, dependency management, dead-code cleanup, review-speed guidance, and post-review practices. Using it without a narrower objective could produce excessive findings or recommendations outside the requested change.
6. The approval standard differs from a readiness-only report. The skill encourages approving changes that improve overall code health. A readiness assessment should instead report evidence and findings while leaving the final decision to the human reviewer.
7. Verification must be evidence-based. The skill asks reviewers to verify tests and builds, but a readiness workflow must distinguish tests that passed, failed, were blocked, or were not run. Source inspection alone is not proof of successful execution.
